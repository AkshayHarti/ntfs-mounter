Your Mac can read NTFS. It cannot write to it.

Apple's built-in NTFS driver mounts Windows disks read-only. Copying a file off one works. Copying a file onto one does not — and every workaround asks you to give up something you probably wanted to keep.

534 tests · MIT licence · macOS only · no kernel extension, no SIP change, no reboot

What the workarounds cost

  • A commercial driver. Paragon NTFS for Mac and Tuxera NTFS work, and both are paid, closed-source kernel extensions. That is a reasonable trade for a studio; it is a lot of trust for one external drive.
  • macFUSE plus ntfs-3g. The long-standing free route. macFUSE installs a kernel extension, which means reducing macOS startup security and rebooting. It also puts a kernel component between your data and the disk.
  • Reformat to exFAT. Removes the problem by removing the filesystem. You lose journaling, POSIX ownership, and the behaviour that made the disk NTFS in the first place.
  • A Windows VM or a second machine. Correct, isolated, and far more work than copying a file. It also does not help a script that needs the disk mounted on this Mac.
  • Terminal recipes. The sudo one-liners that mount NTFS read-write usually work until the disk is dirty, hibernated, or unmounted badly — then the volume is left half-mounted and the next attempt fails for a different reason.

The people who hit this are not edge cases: camera cards formatted on Windows, external SSDs shared between platforms, Boot Camp partitions, and anyone who receives a drive from a Windows user. The request is small — write one file, safely — but the filesystem does not offer a small answer.

The solution: a userspace mount with explicit edges

ntfsmnt mounts one NTFS volume read-write through FUSE-T and the FUSE-T build of ntfs-3g. FUSE-T is a userspace filesystem layer: no kernel extension, no startup-security change, no reboot. The mount is real — ordinary reads and writes work — but nothing is added to the kernel to make it happen.

What makes it usable is not the mount. It is the set of edges around it:

  • One volume at a time. ntfsmnt replaces Apple's mount for a single device, by label, UUID, or device path. Duplicate labels raise an error instead of guessing, and a mount that belongs to another volume is never evicted to make room.
  • No write without proof. After mounting, it writes a small probe file, reads it back, deletes it, and checks that the mount point is owned by the invoking user. Success means the write actually landed.
  • Failure restores the read-only mount. ntfsmnt has to evict Apple's mount to take the volume. Every failure path puts the read-only mount back before returning, and a message that claims "restored" is only printed when the mount table confirms it.
  • No automatic repair. It never runs ntfsfix, ntfsresize, mkntfs, or ntfswipe. Hibernated and dirty volumes are refused by default; --recover and --remove-hiberfile are opt-in, and the destructive one requires the volume label typed by hand.
  • No kill -9. Unmount sends one SIGTERM after a normal unmount reports busy. Disk processes are never force-killed.

Those rules are not documentation only. They are invariants in AGENTS.md, and the test suite exercises the failure paths through injected runners, so the mount and unmount sequences run without a real disk.

When an agent asks, a human grants

The same core is exposed four ways: a command line, a loopback-only web dashboard, a menu-bar app, and an MCP server over stdio. The first three are for a person at the machine. The fourth is for an agent, and it is where the design gets strict.

ntfsmnt mcp runs as the unprivileged user and holds only an agent token. Nine tools are exposed: three read tools that work anywhere, and six action tools for mount, unmount, eject, and grants. Every action needs a grant that is:

  • Narrow. Bound to one volume and the specific actions requested, with a short lifetime.
  • Approved by a human. A single-use nonce opens a browser page; the agent token cannot approve, deny, or mint a grant.
  • Audited in two phases. An attempt line is written before the operation runs, and an ok or fail line after. If the audit log cannot be written, the mount and eject fail closed.
  • Never destructive. --recover and --remove-hiberfile are not reachable from any tool or grant route. The two flags that can damage data stay human-only.

The agent can ask; it cannot help itself. That is the whole point of the split: the useful 90% becomes callable, and the irreversible 10% keeps a person in the loop.

What it does not do

  • It is not a general NTFS driver. One volume at a time, on macOS, with FUSE-T and ntfs-3g installed by the setup script. If you need several NTFS volumes mounted at once, this is the wrong tool.
  • It is not a repair tool. A damaged volume needs Windows or a deliberate recovery workflow, not a mount with extra flags.
  • The menu-bar app is unsigned. Notarization needs an Apple Developer ID. The app works without it, but macOS will ask you to confirm the first launch.
  • Real-disk coverage is narrow. The test suite is hermetic; the manual acceptance procedure runs on one real NTFS volume with root and Full Disk Access. A wider disk matrix is future work, not a claim.

Install

From a checkout
git clone https://github.com/AkshayHarti/ntfs-mounter.git && cd ntfs-mounter && ./scripts/setup.sh
PyPI
uv tool install "ntfsmnt[web]"
For an agent
uvx ntfsmnt mcp — after the one-time sudo ./scripts/install-privileged.sh
Then
ntfsmnt list shows each volume's label; ntfsmnt mount <label> takes that one read-write. The label is whatever the disk is called — HD1, Windows, SDCARD — not a fixed name. A UUID or device path works too.

Status. The grant-scoped MCP server is merged and the 0.2.0 release is in progress. PyPI still serves 0.1.0, which has the CLI and the web UI but no MCP server. The checkout install is the reliable way to try the agent path today.
