Three ways to give an agent disk hands

Same product brief, three architectures. The winner is not the most powerful one — it is the one whose install is one line, whose authority is narrow, and whose upgrade path is a packaging change, not a rewrite.

Pick one starting shape

All three expose the same verbs — mount, unmount, eject, doctor, grant. They differ in where the lock, the grants, and the audit live.

Option A Start here

Toolbelt

One stdio MCP process per agent session. Everything lives in a library: grants, lock, audit. No daemon, no ports, no lifecycle.

The wedge, then the upgrade

Ship A. Move the lock, grants, and audit into a library on day one so B is a packaging change, not a rewrite. Ignore C until a second capability is real.

Recommendation: build A, but put the grant, lock, and audit logic in ntfsmnt/ — not in the MCP adapter. The adapter should be disposable. That single boundary is what makes B cheap and C possible without rewriting the safety model.

What makes it spread

  • One-line install — uvx ntfsmnt[mcp]; no daemon, no app, no account.
  • Directory-first launch — MCP registry, Smithery, awesome-mcp lists, one canonical server.json.
  • 30-second video — “Claude, mount this drive and copy the footage,” with the grant card on screen.

Proof people can share

  • Signed operation receipt — a small shareable card: volume, bytes copied, grant used, zero repair tools.
  • Zero-hardware demo — ntfsmnt demo attaches a bundled NTFS image, so the hero demo runs anywhere.
  • Agent-readable manifest — llms.txt + tool descriptions written for models, not just humans.
